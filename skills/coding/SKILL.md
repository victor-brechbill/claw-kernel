# Coding Skill — Main Agent Orchestration

> **This skill is exclusively for the main agent. Developer and Code Review agents have their own skills.**

> ⚠️ **Dashboard Availability:** This workflow can optionally integrate with a dashboard for kanban management. Without a dashboard, tasks come from the user in chat and IDs are assigned manually.

## Purpose

Orchestrate the full coding workflow: pick tasks, triage, spawn developers, review, merge, and clean up.

---

## 🔴 CRITICAL: User Never Reviews Code

**The user does NOT review PRs. Code review is ALWAYS done by the code-reviewer agent.**

- ❌ NEVER say "waiting for the user's review" about code
- ❌ NEVER ask the user to review a PR
- ❌ NEVER wait for the user to approve code changes
- ✅ ALWAYS spawn code-reviewer agent for PR review
- ✅ Code-reviewer agent approves and you merge (or handle feedback)
- ✅ User only gets involved for: decisions on findings, escalations after 2+ retry failures, or non-code questions

**The "review" column in kanban can mean:**

1. **Code PR exists** → Needs code-reviewer agent spawn (NOT user)
2. **Investigation/research complete** → Needs user's decision on findings/approach

**User's role:** Product decisions, prioritization, approving investigations/findings. NOT code review.

## Ticket IDs

Ticket IDs follow the format `{PREFIX}-{number}` (e.g., `TASK-001`, `TICKET-042`, `NOVA-123`).

**The PREFIX is configurable** — common choices:

- `TASK` — Generic task tracker
- `NOVA` — Example from the reference implementation
- `DEV` — Development tasks
- Custom prefix matching your project name

**When a Dashboard is available:**

- IDs are auto-generated by the dashboard
- Dashboard URL is typically configured in your workspace (e.g., `http://localhost:3080` or your deployed domain)

**Without a Dashboard (manual mode):**

- The main agent manually assigns IDs starting from `{PREFIX}-001`
- Increment sequentially for each new task
- Track assignments in a local file or active-tasks.json registry

## Concurrency Rules

**Agent Concurrency (Per Project):**

- Max **1 Developer** agent per project at a time
- Max **1 Reviewer** agent per project at a time
- Developer + Reviewer **CAN run concurrently** on the same project (they work on different branches)
- Agents on **different projects** can always run concurrently
- Check `sessions_list` before spawning — if a developer is already running on that project, wait

**Feature Branches for EVERY Change:** No direct pushes to main, ever.

- Developer creates feature branch: `ns-XXX-description` or `{prefix}-XXX-description`
- Developer creates PR from feature branch
- Code Review agent reviews the PR
- If passed, merge to main

This ensures proper review and prevents broken code from reaching main.

**Fresh Sessions for Every Task:** ALWAYS spawn a new session for each task. Never reuse an existing developer session.

- Each `sessions_spawn` creates a unique subagent session (e.g., `agent:developer:subagent:{UUID}`)
- This ensures the agent starts with a clean context, avoiding token limit overflows
- If a developer agent's session hits context limits, the solution is to spawn a fresh one
- Long-running sessions accumulate context and will eventually overflow — fresh sessions prevent this

## Workflow Steps

### Step 1: Pick a Task

**When a Dashboard is available:**

- Query the Kanban backlog API at your configured dashboard URL
- Pick the highest-priority unassigned task
- Assign it to yourself, move to "In Progress"

**Without a Dashboard (manual mode):**

- Tasks come from the user directly in chat
- Track tasks in a local markdown file or the active-tasks.json registry if needed

### Step 2: Triage

Evaluate the task scope:

**Small task** (bug fix, minor feature, config change):

1. Create a GitHub issue in the appropriate repo
2. Write clear acceptance criteria in the issue body
3. Assign a ticket ID: `{PREFIX}-{number}`
4. Proceed to Step 3

**Large task** (new feature, multi-file change, architectural work):

1. Assign a ticket ID: `{PREFIX}-{number}`
2. Write a full PRD — proceed to Step 2b

### Step 2b: PRD Process

1. Create PRD file at `~/clawd/coding/prds/{PREFIX}-{id}-prd.md`
2. PRD structure:

   ```markdown
   # PRD: {PREFIX}-{id} — {Title}

   ## Problem Statement

   [What problem does this solve?]

   ## Goals

   [Bullet list of goals]

   ## Non-Goals

   [What this does NOT include]

   ## Technical Approach

   [High-level implementation plan]

   ## Requirements

   [Numbered list of specific requirements]

   ## Acceptance Criteria

   [How do we know it's done?]

   ## Open Questions

   [Anything needing clarification]
   ```

3. Send the user a summary message:

   ```
   📋 PRD Ready for Review: {PREFIX}-{id} — {Title}

   {2-3 sentence summary}

   Full PRD: [file path or inline]

   Approve to proceed, or reply with feedback.
   ```

4. **Wait for the user's explicit approval in chat** before proceeding
5. On approval, create GitHub issue(s) referencing the PRD
6. Proceed to Step 3

### Step 3: Spawn Developer Agent

**⚠️ BEFORE spawning — check for repo conflicts:**

1. Run `sessions_list` to find active developer agents
2. Check their labels/status files to see which repos they're on
3. If the target repo already has an active developer → STOP, queue this task for later

Determine the branch name:

- Feature: `feat/{PREFIX}-{id}-{short-description}`
- Bug fix: `fix/{PREFIX}-{id}-{short-description}`
- PRD-based: `prd/{PREFIX}-{id}-{short-description}`

Spawn a subagent with label `{PREFIX}-{id}-description`:

**After spawning, extract unique ID from session key and include in task:**

```
After spawn returns childSessionKey like "agent:developer:subagent:097cb5ee-..."
Extract: uniqueId = "dev-" + key.split(":")[3].slice(0, 8)
```

**Task message to Developer agent — MUST include explicit completion criteria:**

```
## Task: {PREFIX}-{id} — {Title}

**Type:** [GitHub Issue | PRD]
**Link:** [issue URL or PRD file path]
**Project:** [repo name]
**Branch:** {branch_name}
**Working Directory:** /home/ubuntu/dev/{project}/

### Requirements
[Copy requirements/acceptance criteria here]

### Context
[Any additional context, related files, architecture notes]

### ⚠️ Completion Checklist — Do ALL of these before exiting
You MUST complete every step below before your session ends:
1. [ ] Launch Claude Code, review its plan, approve it, and WAIT for it to finish
2. [ ] Verify the code changes (type-check, build, review diffs)
3. [ ] **Run unit AND integration tests** and ensure all pass. Tests are NOT run in CI — this is YOUR responsibility! Only run E2E tests if the change impacts something covered by an E2E test set.
4. [ ] Update project documentation (CLAUDE.md, etc.)
5. [ ] **Commit ALL changes:** `git add --all && git commit -m "{PREFIX}-{id}: {description}"`
   - **ALWAYS use `git add --all`** (or `-A`) to stage everything, including new files
   - **NEVER selectively stage files** — if something shouldn't be committed, add it to .gitignore
   - This prevents the "untracked file" bug where new scripts/files are created but never committed
6. [ ] Update status file with final state: `completed` or `failed`
7. [ ] Include in status file: branch name, commit hash, summary, test results, any issues
8. [ ] Kill all background processes (Claude Code, monitor, dev servers)

Your session can run for up to 1 hour. DO NOT exit after launching Claude Code —
stay alive and poll until it finishes. Launching Claude Code is step 4 of 10 in
the vibecoding workflow.

Write status updates to: ~/clawd/coding/status/{PREFIX}-{id}-dev.md
```

**For UI-heavy projects, ADD THIS SECTION:**

```
### 📸 UI Changes — Screenshot Requirement

**CRITICAL:** If this task modifies ANY UI components, you MUST include screenshots:

1. **Before screenshots:** Take screenshots of the current UI state BEFORE making changes
   - Document what it looks like now
   - Use a headed browser (not headless) — you need to actually SEE it

2. **After screenshots:** Take screenshots AFTER implementation
   - Show the new UI state
   - Verify visual correctness with your own eyes

3. **Include in PR description:** Add both screenshots under a "## Screenshots" section
   - Use markdown image syntax: `![Description](path/to/screenshot.png)`
   - Or upload directly to GitHub when creating the PR

**Why this matters:**
- Forces you to visually verify your work (catches layout bugs, alignment issues)
- Makes code review faster (reviewer sees what changed instantly)
- Documents the change visually for future reference

**Missing screenshots for UI changes = incomplete work.** The code reviewer will flag this as a blocking issue.
```

**⚠️ Always set `runTimeoutSeconds: 3600`** (1 hour) when spawning developer agents. Claude Code sessions routinely take 10-20+ minutes.

### Step 4: Monitor Developer Agent & Hand-Off

The Developer agent runs as a sub-agent. Clawdbot automatically notifies you when it completes (the "background task completed" system message). You do NOT need to actively poll — just wait for the notification.

**When the Developer agent completes:**

1. **Read the status file** at `~/clawd/coding/status/{PREFIX}-{id}-dev.md`
   - Check `State`: `completed`, `failed`, `blocked`
   - Get: branch name, commit hash, summary, test results
2. **If `completed`:** Proceed to Step 5 (Gut-Check Review)
3. **If `failed`:** Read the failure details, decide whether to retry or escalate
4. **If `blocked`:** Evaluate the blocker, provide guidance or escalate to the user
5. **Run stray process cleanup** (see Process Cleanup section below)

**If the agent exits unexpectedly (no status file or empty findings):**

1. Check `sessions_history` for the agent's session to see what happened
2. Check for stray Claude Code processes: `ps aux | grep "[c]laude" | grep -v clawdbot`
3. Kill any strays, then decide whether to re-spawn

**The status file IS the hand-off artifact.** The Developer agent writes it; the main agent reads it. No pinging or cross-session messaging needed. This keeps the workflow clean and non-interruptive.

### Step 5: Gut-Check Review

When the Developer reports completion with a PR link (or direct commit):

1. Read the PR diff (use `gh pr diff {number} --repo {repo}` or `git show --stat {commit}`)
2. Quick sanity checks:
   - Does the diff look reasonable in size for the task?
   - Any obvious red flags (hardcoded secrets, giant binary files, deleted critical files)?
   - Does the branch name match conventions?
   - Are there tests?
3. **🚨 Check for binaries/blobs:**
   ```bash
   # Check for compiled binaries in the commit
   git diff --name-only origin/main | xargs -I{} file "{}" 2>/dev/null | grep -E "executable|ELF"
   # Check commit stats - huge additions are a red flag
   git show --stat {commit} | tail -5
   ```

   - If 100s of files changed or 10k+ lines for a small task → investigate
   - If any ELF/executable files → STOP, they shouldn't be committed
4. If something looks clearly wrong, send back to Developer with feedback (counts as a retry)
5. If it looks reasonable, proceed to Step 6

### Step 5b: Rebase Before Review (If Needed)

Before spawning the Code Reviewer, check if the feature branch needs rebasing:

```bash
git fetch origin
git log --oneline origin/main ^origin/{feature-branch} | head -5
```

If main has moved ahead (new commits since branch was created):

1. **Simple case:** `git checkout {branch} && git rebase origin/main`
2. **Conflict case:** Resolve conflicts or cherry-pick the feature commit onto fresh main

**Why this matters:** Stale branches can have merge conflicts or miss important changes from recently merged PRs. Rebasing ensures the code review happens against current main.

**Task message to Code Review agent:**

```

**PR:** {pr_url}
**GitHub Repo:** {owner}/{repo}
**Original Task:** [GitHub Issue URL | PRD file path]
**Type:** [issue | prd]
**Project:** {repo_name}

### Requirements to verify
[Copy requirements/acceptance criteria]

### Original Task Context
[Paste the full PRD content or issue description here — the reviewer needs this for Phase 1-2]

### Review Instructions
1. Your AGENTS.md in ~/clawd-code-reviewer/ is your complete manual. Read it.
2. **Phase 1: Context Understanding** — Summarize what this PR does and why before reviewing code
3. **Phase 2: Solution Validation** — Evaluate the approach (PROCEED/RETHINK/REJECT/EXPAND)
4. **Phase 3: Code Review** — Only if Phase 2 = PROCEED. Full review for quality, correctness, security
3. Run unit AND integration tests (capture output for the review). Only run E2E tests if the change impacts something covered by an E2E test set.
4. **Submit a GitHub review with inline comments** — be thorough!
   - Add lots of comments: questions, observations, issues, praise
   - Include test output at the end of your review
5. Submit with: `--approve` (PASS), `--request-changes` (FAIL), or `--comment` (borderline)
6. Write local report to: ~/clawd/coding/status/{id}-review.md

**⚠️ You MUST submit an actual GitHub review, not just a local file!**
The main agent will then review your comments, acknowledge them, and make the final merge/reject decision.
```

**For UI-heavy projects, ADD THIS:**

```
### 📸 Screenshot Verification (Required for UI changes)

**Check the PR description for screenshots:**
1. If the PR modifies ANY UI components, screenshots are REQUIRED
2. Look for a "## Screenshots" section in the PR description
3. Must include BOTH:
   - Before: What it looked like before changes
   - After: What it looks like now

**If UI was changed but screenshots are missing:**
- This is a BLOCKING issue
- Request changes with: "Missing required screenshots for UI changes. Please add before/after screenshots to the PR description."
- The developer must add screenshots and update the PR

**Why this matters:**
- Verifies the developer actually tested the UI visually
- Allows faster review (see changes without running code)
- Catches visual bugs (alignment, spacing, colors, responsive issues)
```

### Step 7: Review the GitHub Review & Take Action

The Code Reviewer submits a formal GitHub review with inline comments. **The main agent must review these comments and take action.**

> 🎯 **Quality Over Speed — Always.** Code reviewers often mark improvements as "non-blocking" or "minor suggestions." These are still valuable improvements! We are already shipping at an incredibly fast pace — we can afford to do things right. Evaluate each suggestion: if it's a good idea, **implement it now** (preferred) or capture it in a backlog card for larger items. We write quality code, enhance features, and continuously improve. Never skip good suggestions just to merge faster.

#### 7a. Review the PR and Comments

```bash
# View the PR and its reviews
gh pr view {pr_number} --repo {owner}/{repo}

# List all reviews
gh pr reviews {pr_number} --repo {owner}/{repo}

# View the diff to understand context
gh pr diff {pr_number} --repo {owner}/{repo}
```

Read through:

1. The Code Reviewer's overall review summary
2. All inline comments (questions, issues, suggestions)
3. The test results pasted in the review

#### 7b. Acknowledge/Respond to Comments

**For each inline comment, the main agent should:**

1. **Questions:** Answer them if you know, or note they need the user's input
2. **Valid Issues:** Acknowledge and decide: fix now or create follow-up card
3. **Suggestions:** Accept, reject with reason, or defer to follow-up
4. **False Positives:** Dismiss with explanation

You can reply to comments via the GitHub API or web UI. At minimum, ensure no comments are left hanging.

#### 7c. Make the Final Decision

**If Code Reviewer APPROVED (PASS):**

1. **Review their comments** — make sure nothing critical was missed

2. **🔍 Evaluate Every Suggestion** — Quality over speed, always.

   For EACH suggestion/recommendation in the review, ask:
   - Is this a good suggestion? Would it improve the code or functionality?
   - Does it fit the scope of this PR, or is it a separate concern?

   **🚨 EVERY good suggestion MUST be implemented. No exceptions.**

   | Good Idea? | Fits Scope?                 | Action                                                                        |
   | ---------- | --------------------------- | ----------------------------------------------------------------------------- |
   | Yes        | Yes                         | **Pass back to Developer** — implement now ✅                                 |
   | Yes        | No (large/separate concern) | **Create backlog card** — capture for later                                   |
   | No         | —                           | **Skip** — note why in PR comment (rare — most reviewer suggestions are good) |

   **Default action: ALWAYS IMPLEMENT.** Never skip a good suggestion to merge faster. Never label improvements as "noted for future cleanup" or "non-blocking." If the reviewer identified a way to make the code better, the code should be made better NOW.

   We are building a clean, robust, maintainable codebase. Speed is not the objective. Quality is. Every reviewer suggestion is an opportunity to improve. Skipping them is technical debt we choose not to take on.

   **Passing back for suggestions (the standard path):**
   - Do NOT merge yet
   - Spawn Developer agent with:
     - The PR link
     - List of suggestions to implement
     - Instructions: "Implement these review suggestions, then push to same branch"
   - Re-run Code Review after fixes
   - This ensures we ship quality code and continuously improve

   **Creating backlog cards (only for genuinely out-of-scope items):**
   - Use VERY sparingly — only for suggestions that are truly separate features or architectural changes
   - If you're unsure whether it fits scope, it probably does — implement it
   - Create a new card with clear description
   - Reference the original PR/task
   - Add as a comment on current card: "Suggestion X captured as Card #Y"

3. **Wait for CI to Pass** — ALWAYS check before merging:

   ```bash
   # Check CI status
   gh pr view {pr_number} --repo {owner}/{repo} --json statusCheckRollup

   # Look for all checks with status="COMPLETED" and conclusion="SUCCESS"
   # If any checks are PENDING, IN_PROGRESS, or FAILED → WAIT, don't merge
   ```

   **Never merge until:**
   - ✅ All required CI checks pass (build, lint, tests, gitleaks, etc.)
   - ✅ Code review approved
   - ✅ No merge conflicts

   **If CI fails:** Investigate the failure, spawn developer to fix, re-review after fix.

4. **Approve and Merge the PR** (only after CI passes AND suggestions are handled):

   ```bash
   # Get the reviewed HEAD SHA from the reviewer's report (ensures we merge exactly what was reviewed)
   REVIEWED_SHA=$(gh pr view {pr_number} --repo {owner}/{repo} --json headRefOid -q .headRefOid)
   # Approve (if using an automated GitHub account for the main agent)
   gh pr review --approve {pr_number} --repo {owner}/{repo} --body "Approved by main agent after code review."
   # Merge — pin to reviewed commit SHA for safety
   gh pr merge {pr_number} --repo {owner}/{repo} --squash --delete-branch --match-head-commit "$REVIEWED_SHA"
   ```

5. **Update the Kanban:**
   - Move card to "Done"
   - **ALWAYS add a comment with the PR URL:**
     `✅ Completed! PR: https://github.com/{owner}/{repo}/pull/{number}`
   - ⚠️ **Never mark done without a clickable link!**

6. Notify the user if it was a significant feature
7. Clean up status files
8. Pick next task (return to Step 1)

**If Code Reviewer REQUESTED_CHANGES (FAIL):**

1. Read the review report and inline comments carefully
2. Decide if you agree with the findings:

   **If you AGREE with the findings:**
   - Check retry count
   - **Retry 1 or 2:** Spawn a NEW Developer agent with:
     - Original task requirements
     - Link to the PR with review comments
     - Explicit list of issues to fix (copy from review)
     - The existing branch (don't create a new one)
     - Instructions: "Address the code review feedback, then push to the same branch"
   - **Retry 3+ (after 2 failed retries):** Escalate to the user

   **If you DISAGREE with the findings:**
   - You can dismiss the review and merge anyway (use judgment!)
   - Document why you overrode the review
   - Only do this for minor/stylistic disagreements, never for real bugs

**If Code Reviewer submitted COMMENT (borderline):**

1. Review their concerns
2. Make the call: merge, request fixes, or escalate to the user

**If Code Reviewer returned RETHINK (Phase 2 early exit):**

1. Read the reviewer's alternative approach suggestion
2. Evaluate: is the alternative genuinely better?
   - **If yes:** Spawn a NEW Developer agent with the new approach. Close the current PR.
   - **If no:** Override — spawn a new reviewer with instructions to skip Phase 2 and proceed to code review.
3. Document reasoning either way

**If Code Reviewer returned REJECT (Phase 2 early exit):**

1. Read the reviewer's reasoning
2. Compare the PR against the original task — is the reviewer right?
   - **If yes:** Close the PR. Re-evaluate the task requirements. May need to rewrite the PRD.
   - **If no:** Override — re-review with clarification.
3. Escalate to the user if unclear

**If Code Reviewer returned EXPAND (Phase 2 early exit):**

1. Read the reviewer's recommendation for expanded scope
2. Evaluate: does this really need to be bigger?
   - **If yes:** Close the PR. Create a new card for the larger effort with the expanded scope.
   - **If no:** Override — the current scope is intentional. Re-review with clarification.
3. Document reasoning

## Process Cleanup — Stray Process Check

**After any agent completes or dies, the main agent MUST verify no stray processes were left behind.** Developer agents are expected to clean up after themselves, but this is the second safety layer.

### When to Run Cleanup Check

- After a Developer agent completes (success or failure)
- After a Code Review agent completes
- When an agent session disappears unexpectedly (crash/timeout)
- During heartbeat checks if any coding task was recently active

### Cleanup Procedure

```bash
# Check for stray Claude Code processes
ps aux | grep -E "[c]laude" | grep -v "clawdbot"

# Check for stray monitor scripts
ps aux | grep -E "[c]laude-code-monitor"

# Check for stray dev servers started by agents
ps aux | grep -E "[n]ode.*dev|[g]o.*run|[n]pm.*start"

# Check for leftover PID/log files
ls /tmp/claude-code-monitor-*.pid /tmp/claude-code-monitor-*.log 2>/dev/null
```

**If stray processes are found:**

1. Kill them: `kill <pid>`
2. Clean up PID/log files: `rm -f /tmp/claude-code-monitor-*.pid /tmp/claude-code-monitor-*.log`
3. Log the incident in the status file (so we can improve the agent's cleanup)

**If an agent died unexpectedly:**

1. Run the full cleanup check above
2. Check the agent's session history for what went wrong
3. Check the status file for the last known state
4. Decide whether to retry or escalate to the user

## Git Lifecycle — CRITICAL

**Every task follows this lifecycle. No exceptions.**

```
main ─────────────────────────────────────────────────→ main (updated)
       \                                             /
        └── feat/{PREFIX}-{id}-desc ──(work)──(commit)──┘
                                                    ↑
                                              MERGE & DELETE
```

### Rules

1. **Branch from main:** Every task starts with `git checkout -b <branch> main`
2. **Work on branch:** All commits happen on the feature branch, not main
3. **Merge to main when done:** After review passes, merge the branch to main
4. **Delete branch after merge:** Immediately delete the feature branch
5. **Deploy from main:** Production always runs from `main`, never a feature branch

### After Review Passes (Step 7)

```bash
# 1. Ensure we're on main and up to date
git checkout main
git pull origin main  # if using remote

# 2. Merge the feature branch
git merge feat/{PREFIX}-{id}-desc -m "Merge feat/{PREFIX}-{id}-desc: {summary}"

# 3. Delete the feature branch (REQUIRED)
git branch -d feat/{PREFIX}-{id}-desc

# 4. Push main (if using remote)
git push origin main

# 5. Delete remote branch (if applicable)
git push origin --delete feat/{PREFIX}-{id}-desc
```

### Why This Matters

- **Stale branches cause confusion:** Old branches get out of sync with main
- **Deploying from feature branches is dangerous:** Production diverges from main, fixes get lost
- **Clean branches = clean history:** Easy to see what's deployed vs in-progress

### Red Flags (Check During Heartbeats)

```bash
# List branches that should have been deleted
git branch --merged main | grep -v main

# If this shows old feature branches → they should be deleted
```

⚠️ **If production is running from a feature branch instead of main, that's a bug.** Merge to main and redeploy immediately.

## Sub-Agent Timeout Guidelines

When spawning sub-agents via `sessions_spawn`, always set `runTimeoutSeconds` appropriately:

| Agent Type        | Timeout (seconds) | Timeout (human) | Reason                                                       |
| ----------------- | ----------------- | --------------- | ------------------------------------------------------------ |
| **Developer**     | 3600              | 1 hour          | Claude Code sessions take 15-30+ minutes, some tasks 45+ min |
| **Code Reviewer** | 1800              | 30 minutes      | Reviews typically 5-15 min, complex PRs can take longer      |
| **Tester**        | 1800              | 30 minutes      | UI testing workflows can be exploratory and time-consuming   |

**Default if not specified:** 600 seconds (10 minutes) — too short for most coding/testing tasks!
